# Single-account finance refresh

Refresh the one account in the launcher-appended **Assigned account (authoritative)** block. You have exactly one assigned account. Partial completion of that account is failure, but interacting with any other account is also failure.

## Browser requirements

1. Before inspecting browser connections, check whether Microsoft Edge is open. If Edge is not open, launch Microsoft Edge first, then retry browser discovery.
2. Use the installed ChatGPT browser extension **directly in Microsoft Edge**. Because Edge is Chromium-based, the browser connection may identify itself as Chrome; this is expected and does not mean Google Chrome should be used. Before doing any finance navigation, inspect the available browser connections and confirm that the selected connection directly exposes Edge and its tabs.
3. An Edge tab displaying `SessionDesktop`, Windows App, AVD, Remote Desktop, or another remote-desktop canvas is not a usable finance-browser connection. Never try to control another browser indirectly through such a tab, canvas, streamed desktop, taskbar, or nested window.
4. Create a brand-new Edge tab with the browser extension's tab API (for example, `browser.tabs.new()`) and use that new tab for the finance refresh. Do not claim, navigate, type into, or repurpose any pre-existing Edge tab.
5. Verify that the newly created tab is a directly controllable Edge tab before entering a finance URL. Browser navigation, DOM inspection, clicks, and typing must target that tab through the browser extension, not through screen-coordinate input sent to a remote desktop.
6. If no direct Edge browser-extension connection is available after opening Edge, stop before interacting with any browser page. Ask the user to enable or reconnect the ChatGPT browser extension in Microsoft Edge; do not substitute Google Chrome, Codex's in-app browser, ChatGPT Computer Use, or indirect remote-desktop control.
7. Reuse the new finance tab throughout the run. Additional new tabs may be created through the same direct Edge connection when sites require separate sessions, but existing user tabs must remain untouched.
8. Prefer visible in-page buttons, links, menus, tabs, forms, breadcrumbs, and Back controls for navigation and recovery. Do not refresh or reload the page when an appropriate in-page control is available. A page reload is a last resort only for a clearly stalled or broken page after waiting and inspecting it; never reload during credential submission, an active MFA/approval window, an in-progress form, a document handoff, or another state that could be lost.

## Completion contract

1. Read only the launcher-appended assigned-account JSON. Its `accountId` is the sole ID you may browse, collect, update, or verify. You may GET `http://127.0.0.1:5137/api/finance/state` only to read supporting state for that exact ID and must ignore every other account returned by the API.
2. Complete the assigned account balance first, UFCU income second only when UFCU is the assigned account, and final verification last.
3. Do not finalize the browser or send a final response while the assigned account remains incomplete. Work taking time or an individual tool call timing out is not a completion condition; continue from saved progress.
4. CAPTCHA or truly user-only input with no active approval window are allowed blockers. An MFA push notification with an active approval window is not yet a terminal blocker: keep the assigned account tab open, keep this Codex process alive, and poll that exact retained tab until the approval succeeds or the issuer's displayed approval window expires. Do not send a final response merely because the push was sent. While waiting, inspect the retained tab at least every 10 seconds and proceed immediately when approval is detected. If the site offers a safe resend after expiration, send it once and wait through that complete new window as well. Never send repeated approval requests while an existing one is active.
5. If a CAPTCHA, expired MFA flow with no safe resend, or another genuine user-only blocker remains after the complete waiting procedure, leave the assigned account tab open on the visible actionable blocker and state exactly what the user must do. Keep a handle to the blocked tab. Before browser cleanup or handoff, explicitly include it in the browser keep/handoff list. Do not close it, navigate it away, replace it with a generic handoff tab, or end the Edge session in a way that closes it. Only then may this non-interactive session exit so the next queued account can start.

## Credential source invariant

The authoritative and exclusive credential source is the launcher-appended **Secure credential lease (authoritative)** block. The Finances app creates that short-lived lease from Windows Credential Manager only when this assigned account starts. The lease is independently restricted to the assigned account ID. `finance/data/finance/accounts.json`, the assigned-account JSON, `/api/finance/state`, browser autofill, and process environment variables are metadata or untrusted inputs and must never be treated as credential sources.

- Retain the exact new assigned-tab binding and tab ID created for this account. Every credential fill must target a locator created from that retained tab binding, never the currently active tab and never a tab rediscovered by title or focus.
- Immediately before each fill, verify from the retained tab that its current URL is the legitimate assigned institution login or expected authentication-redirect page. Verify that the locator is visible and enabled; require a password locator to have `type="password"`. Do not fill when any of these checks fail.
- Redeem the username or password from the exact account-scoped endpoint in the launcher-appended secure credential lease block only inside the same short, block-scoped browser-control call that fills a verified locator. POST with the supplied lease header, require `response.ok`, read the response body in memory, clear the locator, and pass that runtime value immediately to `locator.fill(...)`. For a two-step login, redeem the password separately after its page loads.
- Never assign a response or selected credential to a persistent or top-level browser-runtime variable. Never print, echo, enumerate, serialize, copy, log, return, persist, or include either credential value in source code, shell commands, tool-call output, notes, or summaries. Authored browser-control source may contain the temporary lease token and exact endpoint, but never the response body.
- Do not obtain or rely on credentials from the browser, browser autofill, a browser password manager, saved browser passwords, or values that happen to be prepopulated in a login form.
- A different user-selected Edge tab or another foreground application does not affect locator filling into the retained assigned tab and is never a blocker. Do not ask the user to foreground, activate, or click the assigned tab for credential entry.
- Never report `waiting for credentials` or a broken handoff until the exact account-scoped lease request and targeted locator fill have been attempted. Treat an unauthorized lease response as a real launcher error; do not fall back to environment variables or foreground typing.

## Phase 1: Account balances

1. Read the assigned account ID, login URL, kind, currency, and collector notes from the launcher-appended JSON. Prior stored financial values are intentionally withheld so they cannot be mistaken for current institution values. Use that exact ID only with the launcher-appended lease endpoints and block-scoped targeted-locator procedure above. Do not use `/api/finance/state` to discover or queue other accounts.
2. Sign in and continue until the assigned account is refreshed today. Wait and recheck slow or blank pages, especially UFCU. Populate the exact username and password locators in the retained assigned tab through the browser-control runtime, then submit. When the issuer sends an MFA push, keep the process alive and poll the retained assigned tab through the complete approval window as required by the Completion contract; never treat a still-active push notification as a completed blocker.
3. Record only the bullet that matches the assigned account; the other bullets are reference hints and are out of scope:
   - UFCU checking available balance; ignore savings.
   - Amazon Store Card current balance and available spend.
   - Amazon Visa 7321 at Chase current balance and available credit.
   - Best Buy Visa 0112 at Citi current balance, available credit, and limit.
   - RBC USA checking available balance and card 7651 current balance and available credit.
   - Use **Go to Canadian Accounts** for RBC CAD checking, Mastercard 4484, and credit line values and limits. Keep displayed CAD amounts unconverted.
   - For every credit card and loan, attempt to collect the exact current **minimum payment** in dollars, **payment due date** in `YYYY-MM-DD` format, and whether the current minimum payment has already been met. Prefer the account summary and payment page; inspect a readily available current statement when useful, but payment metadata is optional and must never block an otherwise complete balance/amount-owed refresh. Do not infer these values from the balance, an interest-only due date, a prior month, or scheduled payments. If the institution does not display a field or explicitly shows it as unavailable or `N/A`, submit that field as JSON `null` and continue. If the issuer explicitly says no payment is due, save `minimumPayment` as `0` and `minimumPaymentMet` as `true`, and use the displayed payment due date only when one is provided.
   - Follow the launcher-appended **APR handling (authoritative)** instruction exactly. It is generated from this account's configuration. When APR is already configured, reuse that supplied value and do not spend any browser work searching for or revalidating APR. Only search the institution for APR when the appended instruction explicitly says no APR is configured.
4. Only after the required balance or amount owed and the other account-specific required values have been freshly observed on the institution site during this run, POST the assigned account result to `http://127.0.0.1:5137/api/finance/accounts/{accountId}/values`. Capture the `completionToken` returned by that POST for Phase 3. The request must include `observedAtUtc` as the current UTC time of the final direct page observation, `sourceUrl` as the exact HTTPS URL of that directly controlled institution page, `freshObservationConfirmed: true`, and `unchangedValuesConfirmed: false` on the first attempt. A credit-card or loan POST must include the `minimumPayment`, `paymentDueDate`, and `minimumPaymentMet` properties, but each property may be JSON `null` when that value is not displayed or is explicitly unavailable; missing payment metadata is not a failure and must not prevent posting a freshly verified balance or amount owed. It must also include `collectorNotes`: preserve useful existing notes and add a concise `Payment details:` note naming where payment information was checked and which fields were unavailable or `N/A`. Never invent payment values and never POST prior balance values merely to preserve them. If the required current balance/amount owed or another non-optional account value cannot be verified against the site, do not POST values and do not call the completion endpoint; report the refresh as failed so `LastUpdated` remains stale.
5. If the values endpoint rejects the first attempt because every tracked value matches the stored snapshot, do not treat the stored snapshot as verification. Take a second fresh DOM snapshot from the retained institution tab, re-read every required labeled value, set a new `observedAtUtc`, and repeat the same values POST with `unchangedValuesConfirmed: true` only when that second independent live read is still identical. Any discrepancy must use the newly observed values instead. Capture the completion token only from the accepted request.
6. Treat apparent page, input, navigation, and tool failures as transient and retry them. Do not respond to a failure by opening, browsing, or updating another account.

## Phase 2: UFCU income

Run this phase only when the assigned account is UFCU, and only after completing its balance. For every other assigned account, skip directly to Phase 3. Do not use another process's UFCU work as part of this run.

1. Read the stored UFCU income records before opening transaction history. If UFCU already has stored income, treat the latest stored `postedOn` date as a hard historical cutoff: collect only transactions posted after that date. Do not reopen, recount, or re-submit older stored deposits. Use `income.tracking.lookbackStartOn` only when UFCU has no stored income and an initial history import is required.
2. UFCU can take more than a minute to render an authenticated page. After each major UFCU navigation, inspect the page immediately and proceed as soon as it shows a stable actionable state, including a login button or form, an MFA or CAPTCHA prompt, an authenticated account page, or an explicit error. Do not use a fixed 60-second sleep when one of those states is already visible. Only while the page is blank, incomplete, or visibly loading, poll and reinspect it for up to 60 seconds before treating the navigation as a failure. If it is still actively loading at that point, allow another 60 seconds and inspect it again. Do not close or replace a working authenticated tab merely because a shorter tool call timed out.
3. On the UFCU checking transaction page, use **Filter** rather than relying on search or the initially rendered rows. Determine the overall start date: for an incremental refresh, use the day after the latest stored UFCU `postedOn`; for an initial import with no stored UFCU income, use `income.tracking.lookbackStartOn`. If that start date is after today, there is no UFCU income work to collect. Otherwise, create adjacent filter windows of no more than one calendar month from that start date through today. For each window, set its exact Start Date and End Date and set Incoming or Outgoing to **Incoming**. Never query more than one calendar month at a time.
4. Repeatedly select **Load More** until it no longer appears. Confirm the displayed result count agrees with the number of loaded incoming transactions before deciding the history is complete. Search only filters already loaded rows and is not proof that the full range was reviewed.
5. Inspect the complete new-only range. Collect income from **UFCU only**; do not search other accounts for income. Liberty Mutual ACH transactions whose details identify `TYPE: PAYROLL` and Entry Class Code `PPD` are salary deposits.
6. Open every possible income transaction in the new-only range and treat the transaction detail panel as authoritative for its posted date, amount, description, and source transaction ID. Never infer a transaction date or amount from a biweekly schedule, neighboring rows, or an expected count.
7. The biweekly count check applies only to an initial historical import: about 26 or 27 deposits per full 12 months and about 52 or 53 per 24 months. For an incremental refresh, a small or zero count is normal; reconcile only the dates after the latest stored deposit.
8. Before posting a new UFCU deposit, compare it with stored records by source transaction ID when available; otherwise compare the exact account, posted date, amount, and normalized description. Do not POST any previously stored deposit again. Update an older record only when the site shows that exact transaction changed and a supported stable identifier identifies it; otherwise report the discrepancy.
9. Save each genuine positive UFCU income deposit with POST `http://127.0.0.1:5137/api/finance/income` as JSON: `accountId`, `postedOn` (`YYYY-MM-DD`), positive `amount`, `currency` (`USD`), `kind` (`salary` for regular payroll, `bonus` for bonus pay, otherwise `other`), `description`, and `sourceTransactionId` when the site exposes one.
10. Do not record transfers between the user's accounts, cash deposits, credit-card refunds, reversals, merchant adjustments, reimbursements, or non-income credits. Re-submit an existing transaction only when it changed and a stable transaction ID makes the operation an update rather than a duplicate.

Complete steps 4 through 10 for the current monthly window, including every required income POST and verification, before applying the next monthly window. An empty month completes only that month and must be followed immediately by the next unchecked month. Do not enumerate or load several months and defer inspection or writes until later.

## Phase 3: Verification

1. GET `http://127.0.0.1:5137/api/finance/state` and inspect only the assigned `accountId`.
2. Verify that the accepted values POST response contains the freshly observed staged values, the expected `valuesChanged` result, the final observation time, and the institution source host. The values remain staged and are not written to the account record until the completion endpoint succeeds. For an assigned credit card or loan, verify each available staged payment field against the authoritative page or statement inspected during this run, verify unavailable fields remain null, and verify the `Payment details:` collector note records where they were checked. Null optional payment metadata does not prevent completion.
3. When UFCU is assigned, verify that every qualifying deposit found after the latest pre-run UFCU income date was inserted or updated exactly once, then verify the resulting latest payment and applicable 12-month total. Do not re-verify the entire historical ledger during an incremental refresh. Report the incremental range, how many new transactions were inspected, and how many records were inserted, updated, skipped as duplicates, and excluded as non-income. For every other assigned account, skip income verification.
4. If anything is incomplete and is not waiting on CAPTCHA, MFA, or truly user-only input, return to the appropriate phase and continue. After every verification above passes, POST `{ "completionToken": "<token returned by the values POST>" }` to `http://127.0.0.1:5137/api/finance/accounts/{accountId}/refresh-complete`. Treat success from this exact account-scoped endpoint as the atomic commit point that writes the staged values and updates `LastUpdated`. Then GET finance state once more, inspect only the assigned account, and verify that the committed values and `LastUpdated` match the completion response. Never call completion after partial collection, failed navigation, reused prior values, or incomplete verification. Report completion only after this final persisted-state check succeeds.

Use Microsoft Edge through the installed ChatGPT browser extension, following the Browser requirements above. The connection may appear as Chrome because Edge is Chromium-based. Do not use Google Chrome, ChatGPT Computer Use, or Codex's in-app browser.
